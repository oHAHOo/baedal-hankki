# 주문 취소·환불 정책 초안

상태: 구현 기준. 2026-11-28 서버 구현을 추가했으며, 실제 결제사 검증과 제품 화면 연결 여부는 아래 구현 현황 및 환불 구현 안내를 확인한다.

적용 범위: 배달한끼의 온라인 선결제와 만나서 결제. 현재 서버 구현은 토스 테스트 카드 결제, 가게·운영자 전액 취소, 웹훅 수신과 자동 복구를 포함한다. 운영 결제 활성화 전 가게 운영 절차와 고객 안내를 함께 확정한다.

## 1. 기본 원칙

1. 주문 진행 상태, 결제 상태, 취소 요청 이력을 구분한다.
2. 고객 취소가 허용되면 외부 취소 요청 전에 주문을 CANCELING으로 저장·커밋한다.
3. CANCELING에서는 접수·배달 시작·배달 완료를 허용하지 않는다. 가게 화면에도 작업 중단을 표시한다.
4. 통신 오류는 환불 실패나 성공을 의미하지 않는다. 결과를 확인할 때까지 진행 차단을 유지한다.
5. 취소 완료는 토스 최신 조회 결과의 결제 식별자·금액·통화·취소 상태·잔액을 검증한 후 확정한다.
6. 같은 구매 시도의 재시도는 기존 주문·결제를 복구한다. 새 주문 생성과 재청구로 우회하지 않는다.
7. 한 고객의 다른 정상 구매까지 일괄 차단하지 않는다. 동일 구매 시도와 해당 주문에만 제한을 적용한다.
8. 실제 조리는 서버의 접수 성공을 확인한 뒤 시작한다. 화면 클릭이나 접수 요청 전송만으로 조리를 시작하지 않는다.

## 2. 누가 언제 취소할 수 있는가

| 주문·결제 상황 | 고객 직접 처리 | 가게·운영자 처리 | 환불 원칙 |
| --- | --- | --- | --- |
| 결제 준비 전 또는 미승인 확정 | 주문 취소 가능 | 외부 결제 발생 여부를 확인할 수 있어야 함 | 승인 금액이 없으면 금전 환불 없음 |
| 승인 결과 확인 중(CONFIRMING) | 확인 중 안내와 상태 재조회 | 승인 여부를 먼저 확정하고, 취소 의사를 기록해 이어서 처리 | 미승인 확정이면 주문 취소, 승인 확정이면 허용된 취소 요청에 따라 전액 취소 |
| 결제 완료·접수 전(PENDING) | 직접 전액 취소 가능 | 접수와 취소를 같은 주문 잠금으로 직렬화 | 주문 실결제 총액 전액 취소 |
| 취소 처리 중(CANCELING) | 진행 상태 조회·같은 요청 재시도 가능 | 주문 작업 차단, 결과 자동 조회·장애 처리 | 확정 전 완료 안내 금지 |
| 조리 중(COOKING) | 직접 즉시 취소는 차단하고 문의 접수 | 사유와 실제 조리 진행을 확인해 취소·보상을 결정 | 고객 변심을 일괄 자동 환불하지 않으며, 가게 사유는 별도 심사 |
| 배달 중(DELIVERING) | 문의 접수 | 배달 중단 가능 여부와 사고·오배송 여부 확인 | 승인 없이 자동 환불하지 않음 |
| 배달 완료(COMPLETED) | 누락·오배송·품질 문제 문의 접수 | 주문 이력과 증빙을 확인해 보상 여부 결정 | 주문 완료 이력은 유지하고 환불 내역을 별도로 기록 |
| 취소 완료(CANCELED) | 완료 결과 조회 | 늦게 도착한 이벤트가 주문을 되살리지 못하게 함 | 같은 요청으로 추가 환불 금지 |

CONFIRMING에서 취소 의사를 저장하고 주문을 CANCELING으로 전환한다. 워커가 승인 결과를 확인해 후속 취소한다. 요청 수락을 환불 완료로 표시해서는 안 된다.

## 3. 환불 금액과 사유

### 접수 전 고객 취소

* 온라인 결제는 메뉴 금액과 배달비를 포함한 실결제 총액을 전액 취소한다.
* PG 처리 수수료를 고객 환불액에서 임의로 공제하지 않는다. 수수료·가게 정산 처리는 고객 환불과 별도 관리한다.
* 만나서 결제 주문은 서버에서 온라인 환불하지 않는다. 현장에서 이미 받은 금액이 있으면 가게가 수납 사실을 확인해 별도 반환 처리하고 이력을 남긴다.

### 가게 사유

* 품절·영업 종료·주문 수행 불가로 제공하지 못하는 주문은 가게 또는 운영자가 확인한 뒤 전액 취소하는 것을 기본안으로 한다.
* 접수 후에는 고객 취소 API를 재사용해 상태를 강제로 바꾸지 않는다. 별도 가게 취소·운영자 승인 경로를 둔다.
* 실제 조리·배달이 진행 중이면 중단 담당자와 가게 확인을 기록한다. 물리적 배달이 서버 상태 변경만으로 멈춘다고 가정하지 않는다.

### 일부 누락·오배송·품질·지연 분쟁

* 정액·정률의 자동 부분 환불은 초기 범위에 포함하지 않는다.
* 운영자가 제공 내역·고객 요청·가게 확인을 검토해 재제공, 전액 취소 또는 향후 부분 환불 절차로 처리한다.
* 부분 환불 기능 전에는 결제사 관리자 화면에서 임의로 부분 취소해 우리 원장과 불일치를 만들지 않는다. 불가피한 수동 처리는 승인자·금액·사유·결제사 거래번호를 기록하고 대사한다.
* 배달 완료 후 보상 환불을 했다는 이유로 조리·배달 이력을 삭제하거나 주문을 다시 접수하지 않는다.

가게 사유 전액 취소와 운영자 심사 API를 제공한다. 재제공·부분 환불의 자동 산정과 실행은 포함하지 않는다.

## 4. 접수와 취소가 동시에 요청되는 경우

* 서버에서 같은 주문의 잠금을 먼저 획득하고 상태 변경을 커밋한 요청을 기준으로 결정한다.
* 취소가 먼저 허용되면 CANCELING으로 변경하고 접수는 거절한다.
* 접수가 먼저 허용되면 COOKING으로 변경하고 고객 직접 취소를 거절한다. 이 경로에서는 토스 취소를 요청하지 않는다.
* 브라우저에서 버튼을 누른 시각이나 네트워크 도착 순서 자체를 성공 순서로 보장하지 않는다.

## 5. 환불 성공·실패·미확정 처리

| 결과 | 주문 처리 | 고객 안내 | 가게·운영자 조치 |
| --- | --- | --- | --- |
| 토스 전액 취소 확인 | 주문·결제를 같은 DB 트랜잭션에서 CANCELED로 반영 | 결제 취소 확인, 실제 환급 반영은 결제수단별 차이가 있음 | 해당 주문 작업 종료 |
| 토스는 취소했지만 응답 유실 | CANCELING 유지 | 취소 결과 확인 중 | 웹훅과 주기적 조회로 확정, 주문 진행 차단 유지 |
| 환불 요청의 명시적 거절 | 조회로 최신 상태 확인, 취소 요청·차단 이력 유지 | 취소를 완료하지 못해 확인 중 | 원인 분류 후 재처리 또는 담당자 이관 |
| 타임아웃·5xx·조회 불가 | CANCELING 유지 | 결과 확인 중, 새 결제를 요구하지 않음 | 재시도 간격을 늘려 재조회, 장기 미확정 알림 |
| 고객에게 완료 안내 후 실제 카드 취소 반영 지연 | 확인된 결제 취소 결과 유지 | 결제 취소 확인과 카드·은행 반영을 구분 | 결제사 거래 근거로 문의 대응 |

환불 실패·장기 미확정이라는 이유만으로 PENDING/COOKING으로 자동 복원하거나 가게 작업을 재개하지 않는다. 이미 수락한 취소 의사와 현장 작업 여부를 운영자가 확인해야 한다. 상태를 성공으로 강제 변경해 장애를 숨기지 않는다.

토스는 응답 유실 시 결제를 조회하고 같은 멱등키로 재시도하도록 안내한다. 카드 등 결제수단별 환급 반영 기간도 다르므로 서비스가 입금 완료를 임의로 보장하지 않는다.

* [토스 응답 유실·멱등키 안내](https://docs.tosspayments.com/resources/faq)
* [토스 취소 방식과 결제수단별 반영 기간](https://docs.tosspayments.com/guides/v2/cancel-payment)

## 6. 웹훅·자동 조회·운영 처리

1. 서명·전송 시각을 검증한 웹훅을 DB에 저장하고 커밋한 뒤 수신 성공을 응답한다.
2. 워커가 토스 최신 결제를 조회하고 주문번호·결제키·금액·통화·상태·잔액을 검증한다.
3. 기존 주문 잠금을 획득한 후 현재 상태와 비교해 적용한다. 중복 수신은 추가 환불이나 과거 상태로의 복원을 일으키지 않는다.
4. 웹훅이 없어도 오래된 CONFIRMING/CANCELING을 주기적으로 조회한다.
5. 해결하지 못한 작업은 DB에 유지하고 재시도 횟수·오류·다음 시도 시각·담당자를 추적한다.
6. 수동 확인은 결제사 거래 조회 근거를 남긴다. 운영자가 고객 말이나 화면 캡처만으로 환불 완료를 확정하지 않는다.

토스 관리자 등 서비스 외부에서 취소된 결제는 별도 예외 경로로 처리한다. 접수 전이면 진행을 차단하고 취소 결과를 반영한다. 조리·배달 중이면 추가 진행을 보류하고 가게에 긴급 확인을 요청하며, 이미 발생한 비용은 별도 운영 정산 대상으로 남긴다. 완료된 주문은 완료 이력을 유지하고 결제 변경을 기록한다. 외부 취소 조회·진행 보류·DB 알림을 구현했다. 물리적 배달 중단과 제품 화면·외부 알림 채널 연결은 운영에 함께 반영해야 한다.

## 7. 중복 결제와 중복 환불

* 동일 구매 시도를 식별하는 키를 주문 생성부터 사용한다. 같은 키·같은 요청은 기존 주문을 반환하고, 같은 키·다른 내용은 거절한다.
* 동일 주문의 승인·취소는 기존 결제 식별자와 고정 멱등키를 사용한다.
* 미확정 결과가 있으면 먼저 기존 결제 결과를 복구한다. 새 주문을 생성해 다시 결제하라는 안내를 하지 않는다.
* 서로 다른 주문이 실제로 각각 승인된 경우 자동으로 어느 주문이 중복인지 단정하지 않는다. 고객의 별도 구매 여부와 가게 수행 상태를 확인해 취소 대상을 결정한다.
* 전체 환불 누적액이 실결제액을 초과하지 않도록 결제사 거래 내역과 대조한다. 부분 환불 도입 시 별도 환불 원장을 둔다.

## 8. 고객·가게에 보여줄 상태

| 내부 상태/사건 | 고객 표시 | 가게 표시 |
| --- | --- | --- |
| CONFIRMING | 결제 결과 확인 중 · 다시 결제하지 마세요 | 결제 확인 중 · 접수 불가 |
| CANCELING | 취소 처리 중 · 결제 결과 확인 중 | 취소 처리 중 · 접수/조리 시작/배달 진행 금지 |
| 취소 확인 | 결제 취소 확인 · 결제수단에 따라 반영 시간 차이 | 주문 취소 완료 |
| 장기 미확정 | 담당자가 확인 중 · 문의 식별자 제공 | 처리 보류 · 담당자 확인 중 |

프론트엔드 버튼 비활성화와 별개로 모든 제한을 서버에서도 검증한다. 고객과 가게가 표시를 새로 받지 못해도 서버의 제한은 유지한다.

## 9. 운영 수치 제안 — 확정 전

다음 수치는 외부 서비스가 보장하는 시간이 아닌 초기 운영 제안이다. 합의 후 설정값으로 관리한다.

| 항목 | 초안 |
| --- | --- |
| 미확정 결제 탐색 | 1분 간격, 1분 이상 미확정인 건부터 처리 |
| 외부 요청 재시도 | 지수 백오프와 지터 적용, 결제사 호출 제한에 맞춰 조절 |
| 운영자 알림 | 10분 이상 미확정이면 알림·담당자 이관, 자동 조회는 계속 |
| 미결제 주문 자동 만료 | 생성 후 30분을 초기안으로 하되, 승인 중인 건은 제외하고 금전 상태 확인 후 만료 |
| 멱등키 유효기간 경과 | 자동 승인·취소 재호출 중단, 조회·수동 확인으로 이관 |

고객 안내에는 위 숫자를 환급 완료 보장 시간으로 표시하지 않는다.

## 10. 최소 감사 기록

주문 ID, 결제사 주문번호, 취소 요청 식별자, 요청자·권한, 사유, 요청·처리·확정 시각, 이전·이후 상태, 요청·확인 금액, 결제사 취소 거래번호, 재시도·오류·운영자 조치 근거를 기록한다. 카드번호·인증정보·시크릿 키는 기록하지 않는다. 결제 식별자는 운영 권한이 있는 경로에서만 조회한다.

| 같은 주문 취소 재요청·응답 유실 조회 복구 | 구현 |
| 접수·취소 경쟁 제어 | 구현, 자동 테스트와 로컬 MySQL API 경쟁 검증 |
| 실제 토스 승인·전액 취소 전체 흐름 | 아직 검증 완료되지 않음 |
| CONFIRMING에서 취소 의사 저장 후 후속 취소 | 서버 구현·자동 테스트 |
| 웹훅 영속 수신·워커·주기적 복구·운영 알림 | 서버 구현, 알림은 DB·조회 API로 제공. 외부 전송 채널 미연결 |
| 주문 생성 멱등키 | HTTP 헤더 필수, 동시 요청·내용 충돌 검증 |
| 가게 취소·접수 후 전액 보상·운영자 처리 | 서버 API 구현, 부분 환불·재제공 자동 처리 제외 |
| 외부 관리자 취소 감지와 주문 보류 | 조회 복구·onHold·DB 알림 구현 |
| 고객·가게 화면의 상태·작업 차단 안내 | 제품 화면 미구현, 로컬 검증용 화면만 존재 |

## 12. 정책 검증 시나리오

* 접수·취소가 경쟁해도 한쪽만 허용되고, 허용되지 않은 취소는 PG 호출을 하지 않는다.
* PG 취소 성공 직후 서버가 종료돼도 CANCELING을 유지하고 재시작 후 자동 복구한다.
* 웹훅 유실·중복·역순 도착에도 주기적 조회로 현재 결제 상태에 수렴한다.
* 웹훅 작업 저장 실패 시 성공 응답을 보내지 않고, 저장 후 워커 장애는 작업 재처리로 복구한다.
* 취소 실패·장기 미확정 상태에서 가게 접수·배달 API가 계속 차단된다.
* 결제 식별자·금액·통화 불일치 또는 위조 웹훅으로 상태를 변경하지 않는다.
* 동일 구매 시도 재요청은 새 주문·새 청구·추가 환불을 만들지 않는다.
* 조리·배달·완료 후 외부 취소는 이력을 보존하고 담당자에게 전달된다.
* 미결제 자동 만료와 승인 요청이 경쟁해도 승인된 주문을 무환불 취소하거나 취소된 주문을 승인하지 않는다.

정책 확인 후 우선 구현 순서는 웹훅 영속 수신·주기적 복구, 주문 생성 멱등성, 운영 알림·예외 처리이며, 가게 취소와 부분 환불은 정책 범위를 확정한 뒤 진행한다.


상세 API·설정·배포 전 확인은 [환불 구현 안내](refund-implementation.md)를 참고한다.
